# Prompt Evaluation Rubric

> 用途：评估一个提示词是否真的能用于长期 AI 协同开发。

## 1. 五项硬标准

| 标准 | 通过条件 |
|---|---|
| 可定位 | 明确说明适用哪个子系统、哪些文件、哪些入口 |
| 可执行 | 能指导 AI 执行具体步骤，而不是泛泛建议 |
| 可验证 | 给出验证命令、预期结果、失败处理 |
| 可交接 | 输出能被下一个 AI 或开发者接手 |
| 可沉淀 | 结果能写回文档、记忆或注册表 |

## 2. 评分表

| 分数 | 含义 |
|---:|---|
| 0 | 只有话术，没有项目上下文 |
| 1 | 有目标，但无文件路径和验证 |
| 2 | 有路径，但步骤不可执行 |
| 3 | 可执行，但缺少验证和交接 |
| 4 | 可执行、可验证、可交接 |
| 5 | 可执行、可验证、可交接，并能沉淀为长期资产 |

## 3. 检查清单

一个提示词发布前，必须回答：

```text
它解决什么任务？
它属于哪个子系统？
它需要读取哪些文件？
它允许修改哪些文件？
它禁止触碰哪些文件？
它的输出格式是什么？
它的验证命令是什么？
它失败时如何降级？
它如何写回交接或记忆？
```

## 4. 反幻觉检查

如果提示词包含以下语句，必须补来源或删掉：

- “系统已经支持...”
- “所有测试通过...”
- “这里应该是...”
- “通常会...”
- “显然...”

更好的写法：

```text
根据 `文件路径` 当前内容，系统支持...
根据刚运行的 `命令` 输出，测试结果为...
我尚未验证，建议运行...
```

## 5. 迭代流程

```text
设计提示词
-> 用真实任务试跑
-> 记录偏差
-> 补充路由/上下文/验证
-> 再试跑
-> 达到 4 分以上才纳入 00
```

## 6. 00 目录提示词发布标准

只有满足以下条件的提示词才能进入 `00.超级提示词工程`：

- 至少绑定一个真实目录或真实任务类型。
- 至少包含一个验证方法。
- 明确说明输入和输出。
- 明确说明何时不要使用它。
- 能被未来 AI 直接复用，而不依赖当前对话上下文。
