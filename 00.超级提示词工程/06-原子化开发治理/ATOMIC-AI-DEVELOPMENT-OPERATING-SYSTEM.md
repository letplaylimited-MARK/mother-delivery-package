# Atomic AI Development Operating System

> 用途：把自然语言协同开发变成可追踪、可验证、可沉淀的原子化开发系统。  
> 核心目标：让开发者使用母交付包与通用 AI 大模型合作时，不因需求叠加、规格漂移、上下文丢失、幻觉和无验证扩展而失控。

## 1. 核心判断

通用 AI 大模型不是要被母交付包取代。母交付包的价值是给通用 AI 一个稳定的协作环境：

```text
自然语言意图
  -> 需求原子
  -> PRD/SPEC 契约
  -> 任务图
  -> 工具执行
  -> 验证证据
  -> 审计修复
  -> 知识结晶
  -> 长期记忆
  -> 用户交付包
```

真正要防止的是：AI 在长对话中把未确认的想法当成需求，把推测当成事实，把新增功能堆到旧架构上，把一次修复变成连环重构。

母交付包应该把通用 AI 大模型周边的智能体、技能、工作流、LSP、MCP、插件、知识库、CI、测试、评估、安全、发布、观测和反馈系统纳入同一条证据链，而不是把这些能力散落在不同会话和不同工具里。

## 2. 失败模式与控制器

| 失败模式 | 常见表现 | 必须启用的控制器 |
|---|---|---|
| 需求漂移 | 后续对话不断追加功能，原目标被稀释 | REQ 原子编号、变更影响分析、版本队列 |
| 规格漂移 | PRD 写一套，代码做另一套 | SPEC 契约、追踪矩阵、验收用例绑定 |
| 上下文污染 | AI 混用旧报告、归档、副本、聊天记忆 | Context Pack、权威入口、证据规则 |
| 任务堆死 | 多功能并行叠加，没人知道当前先做什么 | WIP 限制、任务图、阶段门 |
| 幻觉完成 | 没跑测试却说完成，没看文件却说支持 | 证据等级、验证命令、未验证标记 |
| 重构失控 | 小需求触发大范围重写 | 改动半径声明、架构审批、行为保持测试 |
| 记忆丢失 | 下次 AI 不知道为什么这样设计 | ADR、HANDOFF、知识结晶、长期记忆 |
| 评审缺席 | 开发角色自己确认自己没问题 | 双轨审查、Q06 风险审计、发布门 |

## 3. 原子 ID 体系

任何长期项目都必须给关键对象编号。没有编号，就无法追踪。

| ID | 对象 | 例子 |
|---|---|---|
| `GOAL-###` | 项目目标 | `GOAL-001 降低用户手动整理文件时间` |
| `USER-###` | 用户/角色 | `USER-001 项目开发者` |
| `SCN-###` | 使用场景 | `SCN-001 新需求进入开发流程` |
| `REQ-###` | 原子需求 | `REQ-014 支持需求变更影响分析` |
| `PRD-###` | 产品条目 | `PRD-006 需求看板` |
| `SPEC-###` | 技术规格 | `SPEC-009 任务状态机` |
| `ADR-###` | 架构决策 | `ADR-003 使用 Markdown + YAML 做轻量账本` |
| `TASK-###` | 执行任务 | `TASK-021 新增追踪矩阵模板` |
| `TEST-###` | 验证用例 | `TEST-011 路径扫描无绝对路径` |
| `AUD-###` | 审计发现 | `AUD-004 README 与代码入口不一致` |
| `FIX-###` | 修复项 | `FIX-004 同步 README 入口说明` |
| `MEM-###` | 记忆条目 | `MEM-002 用户交付包必须有四体系` |
| `REL-###` | 发布项 | `REL-001 用户交付包 v0.1` |

规则：

- 每个 `REQ` 至少绑定一个 `PRD` 或明确标记为暂缓。
- 每个 `PRD` 至少绑定一个 `SPEC`，否则不能进入开发。
- 每个 `SPEC` 至少绑定一个 `TASK` 与一个 `TEST`。
- 每个 `TASK` 完成必须给出验证证据或标记 `未验证`。
- 每个重大 `FIX` 必须回写 `AUD`、`TEST` 或 `ADR`。

## 4. 阶段状态机

```text
INBOX
  -> CLARIFIED
  -> PRD_READY
  -> SPEC_READY
  -> PLANNED
  -> IN_PROGRESS
  -> PAUSED
  -> IN_PROGRESS
  -> VERIFIED
  -> REVIEWED
  -> RELEASED
  -> CRYSTALLIZED

任意状态 -> BLOCKED
任意状态 -> SUPERSEDED
```

| 状态 | 进入条件 | 禁止事项 |
|---|---|---|
| `INBOX` | 用户提出想法或问题 | 不直接承诺工期和实现方式 |
| `CLARIFIED` | 已确认用户、场景、目标、边界 | 不写代码 |
| `PRD_READY` | 有价值、流程、验收指标 | 不跳过 SPEC |
| `SPEC_READY` | 有模块、接口、数据、依赖、风险 | 不直接做大范围重构 |
| `PLANNED` | 有任务拆解、顺序、验证方式 | 不同时启动过多任务 |
| `IN_PROGRESS` | 正在实现或改文档 | 不扩大范围 |
| `PAUSED` | 主动暂停，等待用户确认、验证结果、范围裁决或依赖完成 | 不把暂停任务伪装成完成 |
| `BLOCKED` | 缺少必要信息、依赖、权限、验证环境，或触发停止线 | 不绕过阻塞继续执行 |
| `VERIFIED` | 验证命令或人工检查通过 | 不声称超过证据的结论 |
| `REVIEWED` | 审计与评审完成 | 不绕过 P0/P1 问题 |
| `RELEASED` | 可交付给目标对象 | 不带个人密钥和本机路径 |
| `CRYSTALLIZED` | 决策、经验、风险写入记忆 | 不只留在聊天记录 |
| `SUPERSEDED` | 被更新的需求、规格、任务或修复方案替代 | 不继续沿用旧版本执行 |

暂停与阻塞规则：

- 用户新增需求会改变当前 PRD/SPEC/TASK 时，当前任务进入 `PAUSED`，新增内容先进入 `INBOX` 并做影响分析。
- 验证失败但原因明确且可修复时，当前任务进入 `BLOCKED` 或拆出 `FIX`；不得直接宣称完成。
- 跨文件夹任务缺少 `USO ID`、`ledger_ref` 或 `validation_refs` 时，先进入 `PAUSED`，补齐追踪对象后再执行。
- 依赖外部模型、插件、MCP、LSP、网络或用户权限时，若无法访问，进入 `BLOCKED`，并记录替代方案。
- 旧需求被用户明确替换、产品方向变化或架构决策更新时，旧对象进入 `SUPERSEDED`，并引用替代对象 ID。
- `PAUSED` 恢复必须说明恢复条件已满足；`BLOCKED` 解除必须给出证据；`SUPERSEDED` 不应恢复，只能追踪到新对象。

## 5. 工件流转

| 阶段 | 主要工件 | 推荐落点 |
|---|---|---|
| 需求进入 | 需求原子、澄清问题、用户场景 | 用户交付包 `01-价值体系/`，或项目 `docs/requirements/` |
| 产品定义 | PRD、用户流程、验收指标 | 用户交付包 `02-功能体系/` |
| 技术规格 | SPEC、接口、数据流、依赖 | 用户交付包 `03-结构体系/` |
| 执行计划 | 里程碑、任务图、WIP 限制 | 项目 `docs/plans/` 或 `04-运作体系/` |
| 开发执行 | 代码、配置、迁移、脚本 | 具体项目源码目录 |
| 验证审计 | 测试报告、审计发现、修复记录 | 项目 `tests/`、`docs/audits/`、`HANDOFF.md` |
| 知识沉淀 | ADR、知识结晶、长期记忆 | `03` 知识库、`05` BRAIN-KB、项目 `docs/decisions/` |
| 用户交付 | 四体系、运行说明、验收清单 | `协同通用AI大模型开发交付包/` |

## 6. 阶段门

### Gate A：需求进入开发前

必须回答：

```text
目标用户是谁？
解决什么真实问题？
不做什么？
验收指标是什么？
这个需求属于当前版本还是未来版本？
```

### Gate B：规格进入实现前

必须回答：

```text
改哪些模块？
新增哪些接口/数据结构/配置？
会影响哪些旧功能？
失败时如何回退？
用什么测试证明完成？
```

### Gate C：合并或交付前

必须回答：

```text
运行了哪些验证？
哪些未验证？
有没有本机路径/密钥/个人数据？
PRD/SPEC/TEST 是否同步？
已知风险是否写入交接？
```

## 7. 多任务 WIP 限制

默认限制：

- 同一时间只允许 `1` 个主目标。
- 同一时间最多 `3` 个进行中任务。
- 新增需求不得直接插入当前任务，必须进入 `INBOX` 并做影响分析。
- P0 缺陷可以打断当前任务，但必须记录打断原因。

## 8. 证据等级

| 等级 | 含义 | 可用表述 |
|---|---|---|
| E0 | 未验证，只是推测 | `推测`、`待验证` |
| E1 | 已读文件，有路径证据 | `根据 <文件>` |
| E2 | 已运行命令，有输出证据 | `根据 <命令> 输出` |
| E3 | 已有测试或审计通过 | `已通过 <测试/审计>` |
| E4 | 新环境或交付环境复现通过 | `已在目标环境复现` |

AI 不得把 E0/E1 说成 E3/E4。

## 9. 与工具的关系

| 工具/能力 | 在本系统中的位置 |
|---|---|
| 通用 AI 大模型 | 自然语言理解、推理、生成、规划 |
| 模型路由/降级 | 按任务选择模型，失败时切换备用模型 |
| Agent/角色 | 产品、架构、开发、测试、审计、运维、UX、知识管理 |
| LSP | 代码语义、跳转、诊断、重构辅助 |
| MCP | 文件、知识库、数据库、外部工具调用 |
| 插件/Skill | 可复用工作流与领域能力 |
| RAG/向量/重排 | 检索事实、需求、规格、代码和旧决策 |
| Shell/Test | 真实执行与验证 |
| Git | 变更证据、版本记录、回滚边界 |
| CI/CD | 自动构建、测试、打包、发布和回滚 |
| Security/Compliance | 密钥、依赖、权限、隐私、License、SBOM 检查 |
| Observability/Eval | 日志、指标、trace、Prompt eval、模型 eval、回归评估 |
| Knowledge Graph | 需求、模块、决策、风险之间的关系 |
| Long-term Memory | P0/P1 决策、经验和用户偏好 |

原则：自然语言负责表达意图，工具负责提供事实和执行证据，文档负责承载长期状态。

## 10. 最小可用版本

开发者若不想一开始做太重，至少维护四个文件：

```text
PRD.md
SPEC.md
TASKS.md
HANDOFF.md
```

但只要项目进入持续开发，就必须升级到原子 ID、追踪矩阵、审计记录和长期记忆。
