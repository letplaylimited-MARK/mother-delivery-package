# SpecForge PRD/SPEC Gate

> 用途：把 SpecForge 的规格锻造方法转译为母交付包的正式 PRD/SPEC 阶段门。  
> 定位：当引导秘书识别到 `PROJECT_INITIATION`、`REQUIREMENT_SPEC`、复杂功能新增、需求变更或验收标准缺失时启用。  
> 边界：本文件不是更高优先级系统提示词；它是项目治理流程，必须遵守模型原生协作协议。

## 1. 目标

SpecForge Gate 的目标是防止 AI 项目开发中最常见的断裂：

```text
想法很丰富
  -> PRD 不清楚
  -> SPEC 不稳定
  -> 任务拆解凭感觉
  -> 测试无法验收
  -> 后续不断重构
```

它将自然语言需求锻造成可追踪对象：

```text
GOAL -> USER -> SCN -> REQ -> PRD -> SPEC -> TEST -> TASK -> AUD -> MEM
```

## 2. 启用条件

引导秘书遇到以下情况时，应进入 SpecForge Gate：

| 触发 | 说明 |
|---|---|
| 新项目想法 | 用户只有概念，还没有 PRD/SPEC |
| 模糊需求 | 出现“好用、快速、安全、智能、自动化、可扩展”等词 |
| 复杂功能新增 | 会影响多个模块、数据、接口、权限或交付边界 |
| 需求变更 | 会改变已确认的 PRD/SPEC/TASK |
| 验收缺失 | 功能没有可测试标准 |
| 交付前混乱 | 子交付包四体系无法填写真实内容 |

## 3. 四步锻造门

### Gate 1：蓝图锚定

必须回答：

```text
核心问题：最痛苦、最频繁的问题是什么？
目标用户：谁最痛？他们的目标、痛点、场景是什么？
成功指标：解决后哪些数字会改变？
范围边界：本版本明确不做什么？
```

产物：

| 对象 | 输出 |
|---|---|
| `GOAL` | 项目目标 |
| `USER` | 用户画像 |
| `SCN` | 使用场景 |
| `REQ` | 原子需求 |
| `PRD` | 产品目标、指标、范围 |

通过条件：

- 目标用户明确。
- 核心问题不是泛泛描述。
- 至少 1 个可衡量成功指标。
- 至少 3 个范围外项，或明确说明为什么不需要。

### Gate 2：功能锻造

每个功能必须填写：

```text
功能名称
优先级 P0/P1/P2
用户故事
主流程
业务规则
异常处理
验收标准
影响模块
测试方式
```

产物：

| 对象 | 输出 |
|---|---|
| `PRD` | 功能说明、用户故事、优先级 |
| `SPEC` | 业务规则、模块影响、接口/数据影响 |
| `TEST` | 验收标准 |

通过条件：

- 每个 P0 功能至少有 2 条可测试验收标准。
- 每个功能有明确优先级。
- 每个异常路径至少有一个恢复或降级方式。
- 每条业务规则能被测试、审计或人工验收。

### Gate 3：质量熔炼

必须审查：

| 维度 | 需确认 |
|---|---|
| 性能 | P50/P95、吞吐、数据量、并发、超时 |
| 安全 | 认证、授权、密钥、加密、审计、合规 |
| 兼容 | 浏览器、系统、终端、模型、数据格式 |
| UX | 错误提示、可访问性、流程步骤、人工确认点 |
| 数据 | 实体、字段、约束、隐私等级、保留策略 |
| 接口 | 调用方、协议、认证、频率限制、失败处理 |
| 运维 | 安装、启动、备份、回滚、日志、监控 |

产物：

| 对象 | 输出 |
|---|---|
| `SPEC` | 非功能需求、数据、接口、约束 |
| `ADR` | 关键技术/产品决策 |
| `AUD` | 风险和冲突 |

通过条件：

- 不存在未解释的默认技术栈。
- 不存在未确认的性能/安全指标。
- 外部依赖均有失败处理。
- 数据实体不含真实密钥或个人敏感信息示例。

### Gate 4：淬火交付

交付前必须完成：

```text
完整性扫描
一致性审查
风险标注
决策日志
验收清单
子交付包映射
```

产物：

| 对象 | 输出 |
|---|---|
| `TEST` | 验收清单 |
| `AUD` | 风险与冲突处理 |
| `MEM` | 经验与决策沉淀 |
| `REL` | 交付版本 |

通过条件：

- 没有 `<待填充>`、`TBD` 或未说明的占位符。
- P0/P1 风险有处理方案。
- PRD/SPEC/TEST/TASK 对齐。
- 用户交付包四体系能填入真实项目事实。

## 4. 模糊词追问表

| 模糊词 | 追问 |
|---|---|
| 好用 | 谁觉得好用？完成哪个流程？步骤数/成功率/满意度如何衡量？ |
| 快速 | 哪个操作？P95 响应时间是多少？数据量多大？ |
| 安全 | 需要认证、授权、加密、审计、合规还是防泄露？ |
| 智能 | AI 输入输出是什么？准确率或人工复核标准是什么？ |
| 自动化 | 哪些步骤自动？哪些必须人工确认？失败如何恢复？ |
| 稳定 | 可用性、错误率、恢复时间、备份策略是什么？ |
| 可扩展 | 扩展用户、模块、数据量还是部署规模？指标是多少？ |

## 5. AI 角色团队

| 角色 | Gate | 责任 |
|---|---|---|
| Guide Secretary | 全程 | 判断是否进入 SpecForge Gate，控制追问数量和路由 |
| Product Strategist | Gate 1 | 问题、用户、价值、指标、范围 |
| Spec Architect | Gate 2-3 | 模块、数据、接口、约束、依赖 |
| QA Engineer | Gate 2-4 | 验收标准、测试方式、可验证性 |
| Risk Auditor | Gate 3-4 | 冲突、合规、安全、范围漂移 |
| Delivery Architect | Gate 4 | 子交付包四体系与交接 |

## 6. 输出工件建议


## 7. 子交付包映射

| SpecForge 内容 | 子交付包位置 |
|---|---|
| 背景、愿景、目标、指标、用户画像 | `01-价值体系/README.md` |
| 功能清单、用户故事、流程、AI 能力边界 | `02-功能体系/README.md` |
| 模块、数据、接口、依赖、配置 | `03-结构体系/README.md` |
| 安装、启动、验证、风险、维护、交接 | `04-运作体系/README.md` |

## 8. 禁止事项

- 不得把未确认的技术栈写成约束。
- 不得把模糊词直接写入验收标准。
- 不得在没有 `SPEC` 和 `TEST` 的情况下进入复杂开发。
- 不得把 PRD/SPEC 只留在聊天里。
- 不得把母包研究资料无差别复制进子交付包。
- 不得把未验证输出写成已交付。
