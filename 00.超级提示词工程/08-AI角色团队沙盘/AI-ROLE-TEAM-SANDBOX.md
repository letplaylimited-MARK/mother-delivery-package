# AI Role Team Sandbox

> 用途：把“多角色思考”变成可重复的开发评审流程，而不是让同一个 AI 自说自话。  
> 目标：在重大需求、架构、重构、交付前，用不同角色暴露盲点、压低幻觉、提高方案稳定性。

## 1. 默认角色团队

| 角色 | 来源 | 主要职责 | 何时介入 |
|---|---|---|---|
| 总控协调官 | `00` | 路由、上下文包、阶段门、交接 | 每次复杂任务 |
| 平台主权者 | `05 ROLE-T01` | 治理、边界、重大风险 | 跨系统/高风险决策 |
| 运营总监 | `05 ROLE-T02` | 需求管理、价值沉淀、版本队列 | 新需求和交付规划 |
| 体系协调官 | `05 ROLE-T03` | Skill/MCP/插件/工作流编排 | 多工具协同 |
| 演化工程师 | `05 ROLE-T04` | 路线图、版本演化、技术债 | 长期规划 |
| 首席架构师 | `05 ROLE-S01/Q01` | SPEC、模块边界、接口契约 | 开发前与重构前 |
| 运维官 | `05 ROLE-S02` | 配置、部署、验证、可迁移 | 发布前 |
| 桥接协调官 | `05 ROLE-S03` | 00/01/03/04/05 串联 | 跨文件夹任务 |
| 研究员 | `05 ROLE-Q02` | 调研、竞品、方案比较 | 不确定技术选型 |
| UX 负责人 | `05 ROLE-Q05` | 用户流程和交付体验 | 用户可见功能 |
| 风险审计员 | `05 ROLE-Q06` | 反方审查、安全、幻觉检查 | 每个发布门 |
| 知识管理员 | `02/03` | 知识图谱、长期记忆、知识结晶 | 每次阶段结束 |

## 2. 三种沙盘强度

| 强度 | 适用场景 | 角色组合 | 输出 |
|---|---|---|---|
| 轻量 | 单文件、小修复、文档调整 | 总控 + 审计员 | 风险清单 |
| 标准 | 新功能、跨文件修改 | 总控 + 架构师 + 审计员 + 知识管理员 | 执行方案 + 验证方案 |
| 全面 | 架构变更、母包/用户包交付、长期路线图 | 默认角色团队 | 沙盘报告 + 决策记录 + 阶段计划 |

## 3. 沙盘流程

```text
输入: 用户意图 + 当前上下文包
  -> 角色分配
  -> 各角色提出观点
  -> 风险审计员反驳
  -> 架构师收敛为 SPEC
  -> 运营总监排版本
  -> 知识管理员写入追踪矩阵
  -> 总控输出执行计划
```

## 5. 死锁处理

当角色意见冲突：

| 冲突 | 仲裁 |
|---|---|
| 价值高但技术风险高 | 降级为试验任务，先做原型或 Spike |
| 用户想加但当前版本会失控 | 进入未来版本队列 |
| 架构师要重构，审计员反对 | 写 ADR，要求行为保持测试 |
| 开发者认为完成，审计员认为未验证 | 审计员优先，直到证据补齐 |
| 多工具方案冲突 | 体系协调官选择最小可验证路径 |

## 6. 输出分流

沙盘不只是讨论，必须落到文件：

| 输出 | 写入位置 |
|---|---|
| 新需求 | `TRACEABILITY-MATRIX` 或项目 `docs/requirements/` |
| 技术决策 | 项目 `docs/decisions/ADR-###.md` |
| 执行任务 | 项目 `TASKS.md` 或计划文档 |
| 风险 | 审计报告或 `HANDOFF.md` |
| 长期记忆 | `03` 知识库或 `05` BRAIN-KB |
| 用户交付内容 | 用户交付包四体系 |

## 7. 防止伪多角色

多角色不是换名字重复同一观点。每个角色必须提供不同类型的证据：

- 架构师：模块、接口、依赖。
- 运营总监：用户价值、版本优先级。
- 审计员：失败场景、验证缺口。
- 知识管理员：写入位置、追踪关系。
- 体系协调官：工具、流程、自动化边界。

如果角色观点没有差异，说明沙盘无效，需要重跑。
