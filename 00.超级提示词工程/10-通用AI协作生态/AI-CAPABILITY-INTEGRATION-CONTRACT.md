# AI Capability Integration Contract

> 用途：定义任何智能体、Skill、MCP、插件、LSP、工作流、模型或外部系统接入母交付包时必须遵守的契约。  
> 目标：让所有能力可发现、可调用、可验证、可审计、可交付。

若能力还没有被选定，或用户只是提出“需要什么技能/插件/开源库/工作流”，必须先执行 `SKILL-CONFIGURATION-GATE.md`，完成需求推导、候选寻找、评估矩阵、配置方案和集成测试计划，再进入本契约登记。

## 1. 能力卡片

每个能力必须有一张能力卡：

```yaml
id:
name:
type: model | agent | skill | workflow | lsp | mcp | plugin | api | script | ci | memory | evaluation
owner:
source:
status: experimental | active | deprecated | archived
maturity: L0 | L1 | L2 | L3 | L4 | L5
description:
use_cases:
trigger_terms:
inputs:
outputs:
read_scope:
write_scope:
execute_scope:
dependencies:
config_files:
validation:
failure_modes:
fallback:
evidence_format:
handoff_required:
delivery_allowed:
```

## 2. 调用前检查

调用任何能力前，AI 必须确认：

| 检查项 | 问题 |
|---|---|
| 任务匹配 | 这个能力是否真的适合当前 `REQ/TASK`？ |
| 权限范围 | 它会读、写、执行哪些内容？ |
| 输入完整 | 必需输入是否已经明确？ |
| 输出用途 | 输出会进入代码、文档、记忆、审计还是交付？ |
| 失败处理 | 失败时怎么降级或回滚？ |
| 证据记录 | 调用结果如何写入验证或交接？ |

## 3. 输出证据格式

任何能力输出都必须落到以下之一：

```text
[FACT] 已读文件、数据库、命令、测试或工具返回的事实
[INFERENCE] 基于事实的推断，需要说明依据
[ACTION] 已执行的操作，必须说明影响范围
[VALIDATION] 验证命令、结果、失败原因
[RISK] 风险、限制、不确定性
[HANDOFF] 下一位 AI 或开发者需要接手的信息
```

## 4. 权限等级

| 等级 | 能力 | 示例 |
|---|---|---|
| P0 Read | 只读 | 搜索、读取文件、读取 DB、LSP 诊断 |
| P1 Write Docs | 写文档 | 更新 PRD、SPEC、HANDOFF、README |
| P2 Write Code | 写代码 | 修改源码、测试、配置 |
| P3 Execute | 执行命令 | 运行测试、构建、脚本、MCP |
| P4 Release | 发布/压缩/部署 | 打包、上传、部署、迁移 |
| P5 Sensitive | 高风险 | 删除、密钥、生产数据、账号权限 |

P4/P5 必须有人类确认或明确任务授权。

## 5. 模型接入规则

通用 AI 或本地模型接入时，需要声明：

- 适合任务：规划、代码、审计、写作、检索、视觉、数据分析等。
- 上下文限制：最大上下文、是否适合长文档。
- 工具能力：是否能调用 MCP、浏览器、Shell、LSP。
- 风险：幻觉倾向、代码能力、中文能力、隐私边界。
- 验证：输出必须由测试、文件读取或审计补证据。

## 6. Agent 接入规则

智能体必须声明：

- 角色身份。
- 职责边界。
- 可调用工具。
- 可修改范围。
- 交接格式。
- 与其他角色冲突时的仲裁规则。

智能体不能同时充当开发者和最终审计者，避免自我确认偏差。

## 7. Skill/工作流接入规则

Skill 或工作流必须声明：

- 能力类型：prompt、template、script、MCP 调用、plugin 调用、LSP 事实、复合工作流或混合能力。
- 触发条件。
- 输入模板。
- 阶段门。
- 输出模板。
- 失败降级。
- 是否需要用户确认。
- 是否写入长期记忆。

复杂工作流必须拆成可验证步骤。

如果 Skill 来自开源项目或外部包，必须补充许可证、版本、维护状态、官方文档或仓库来源。无法实时验证时，状态只能是 `experimental`。

## 8. MCP/插件接入规则

MCP 或插件必须声明：

- 工具名称。
- 工具参数。
- 返回结构。
- 错误类型。
- 是否会写入状态。
- 是否依赖网络、账号、密钥或本机环境。
- 是否可在用户交付包中复现。

若工具结果来自外部实时数据，应标记时间和来源。

## 9. LSP 接入规则

LSP 输出应作为代码事实来源：

- 符号定义。
- 引用关系。
- 类型错误。
- 未使用代码。
- 重构影响范围。

AI 不应在未看 LSP/代码证据时声称“这个函数没有被使用”。

## 10. 评估与验收

每个正式能力都需要至少一种验证：

| 能力类型 | 验证方式 |
|---|---|
| 模型/Agent | 任务样例、幻觉检查、输出审计 |
| Skill/工作流 | 试跑记录、阶段门通过率 |
| LSP/MCP/插件 | 命令/API 调用结果、错误处理 |
| 知识库/RAG | 检索命中率、来源引用、过期检查 |
| 代码工具 | 测试、lint、typecheck、构建 |
| 交付工具 | 新环境复现、路径/密钥扫描 |

## 11. 能力退出机制

能力出现以下情况应标记为 `deprecated` 或 `archived`：

- 无法验证。
- 输出长期不稳定。
- 与主工作流冲突。
- 依赖不可用。
- 安全风险不可接受。
- 已有更可靠替代方案。

退出能力时，必须更新能力注册表和相关文档入口。
