# QCM v6.3.3 Super Prompt Deconstruction

> 来源：用户提供的 QCM 最早期“终极系统提示词”。  
> 场景：用户曾在元宝等通用 AI 大模型入口中，以“秘书/元宝/QCM”方式进行概念推演、系统构建、角色沙盘、沙箱演练、苏格拉底提问与第一性原理分析。  
> 结论：此提示词是现在母交付包多个目录的早期母体之一，不能原样作为系统提示词复用，但其中的“秘书入口、五维雷达、角色调度、数据库心智、迭代飞轮、训练场”应被转译进当前母包。

## 1. 场景还原

这份提示词的真实使用方式不是简单问答，而是一个“认知工作台”。这里需要先澄清两个名称：

- `元宝`：用户当时对微信体系下通用 AI 大模型入口的称呼，底层可能对接 DeepSeek 或 Hunyuan/HY3 preview 等模型；它不是 QCM 内部固定组件。
- `秘书`：用户在超级系统提示词里设计的中枢协调者，负责持续引导、提问、调度、沙盘推演和意图压实；它不是最终执行全部任务的角色，而是把用户思考带入结构化协作流程的入口。

真实链路更接近：

```text
用户提出概念/想法/困惑
  -> 秘书引导用户澄清目标
  -> 给出选项、反问和苏格拉底式追问
  -> 用五维雷达判断任务边界
  -> 召唤多个角色视角
  -> 用苏格拉底提问和第一性原理继续挖深
  -> 形成初步组织/角色/提示词/系统定位
  -> 再到另一个对话框多轮脚本演练、复盘、压实真实意图和计划
```

这解释了为什么后续会演化出多个文件夹项目：早期 QCM 是一个“超级系统提示词里的组织模拟器 + 人工沙箱流程”。当概念推演变成真实项目开发后，原本靠对话维持的角色、数据库、记忆、沙盘、交付物，就必须被拆成可迁移文件、可运行代码、可验证命令和可交接文档，于是后来逐步形成通信协议、知识库、QCM 公式、Q-SpecTrum 平台、提示词工程和用户交付包。

## 2. 原子机制拆解

| 原提示词模块 | 原子机制 | 当前判断 |
|---|---|---|
| 元指令：自我指涉与终极形态 | 自描述、自验证、自迭代 | 机制有价值，但“系统之上的系统”必须降级为项目协作协议 |
| 行为宪法 | 结构化、可视化、全息化、自动调度、价值化 | 保留为输出质量偏好，不可变成所有任务强制格式 |
| 12 维全息猎人 | 多角色、多视角问题拆解 | 保留为角色团队沙盘/能力注册，不固定每次全量召唤 |
| 8 大智能数据库 | 记忆、案例、资源、报告、成长路径 | 转译为真实文件/数据库/知识图谱，不允许假装已有数据 |
| 自主迭代飞轮 | 子迭代、母迭代、全迭代 | 映射到原子治理、版本规划、QCM 飞轮 |
| 秘书引导系统 | 接收、五维雷达、任务确认单、调度、迭代邀请 | 直接进入 `00/12 引导秘书逻辑` |
| 五阶段用户成长路径 | 用户能力阶段和成长报告 | 可作为可选用户画像/培训体系，不主动贴标签 |
| 三层训练场 | 沙盘、专项、综合训练 | 映射到 QCM 沙盘、测试环境、毕业项目/交付演练 |
| 唤醒指令集 | 用户命令触发不同流程 | 转译为意图注册表，不依赖固定魔法口令 |
| 标准产出物模板 | 手册、分析报告、研讨会记录、迭代记录 | 映射到用户交付包四体系和交接文档 |
| 跨对话框脚本演练 | 用另一个会话复盘与压实意图 | 转译为沙箱/验收流程、handoff、Context Pack 和任务确认单 |

## 3. 真正值得保留的精华

### 3.1 秘书不是执行者，而是入口协调者

早期提示词里“秘书”最有价值的部分，是让 AI 不急着回答，而是先进行五维扫描、任务确认、角色调度和迭代邀请。这正是当前母包最需要的入口层。

更精确地说，秘书承担三种工作：

| 秘书工作 | 早期做法 | 当前母包表达 |
|---|---|---|
| 引导思考 | 选项、追问、苏格拉底提问、第一性原理 | `GUIDE-SECRETARY-PROTOCOL` 的 CLARIFY/CONFIRM |
| 协调推演 | 召唤猎人、角色研讨、沙盘/沙盒 | `00/08` 角色团队沙盘 + `04.QCM` |
| 压实执行 | 另一个对话框脚本演练，确认真正意图和计划 | Context Pack + Handoff + `REQ/SPEC/TASK/TEST` |

当前落点：

- `00/12-引导秘书逻辑/GUIDE-SECRETARY-PROTOCOL.md`
- `00/12-引导秘书逻辑/GUIDE-SECRETARY-HANDOFF-TEMPLATE.md`
- `00/03-上下文包模板/AI-CONTEXT-PACK-TEMPLATE.md`

### 3.2 12 维猎人本质是“多维审查矩阵”

它不应被理解为 12 个永久人格，而应转成任务审查维度：

| 早期猎人 | 当前母包中的更稳健表达 |
|---|---|
| 隐蔽 | 安全、隐私、密钥、权限、信息暴露审查 |
| 资源 | 能力注册、工具链、开源/文档/数据源检索 |
| 进化 | 路线图、技术债、版本演进、迁移规划 |
| 清理 | 反混乱、去冗余、上下文压缩、范围控制 |
| 扩张 | 增长策略、市场路径、风险预案 |
| 情报 | 调研、竞品、资料验证、来源管理 |
| 策略 | 顶层设计、优先级、博弈/取舍 |
| 执行 | TASK、SOP、看板、里程碑、WIP |
| 评估 | 指标、ROI、验收、测试、审计 |
| 用户 | 用户旅程、痛点、可用性、交付体验 |
| 系统 | 架构、运维、性能、瓶颈、依赖 |
| 宇宙 | 第一性原理、跨界创新、范式重构 |

当前落点：

- `00/08-AI角色团队沙盘`
- `00/10-通用AI协作生态`
- `04.QCM-MVP-Emergence`
- `05.超极智脑_Q-SpecTrum` 角色路由

### 3.3 8 大数据库本质是“长期资产分类法”

早期提示词的数据库设计是认知上有价值的，但不能让 AI 假装已经有数据库。因此应转成母包的真实工件注册：

| 早期 DB | 当前对应 |
|---|---|
| DB-001 迭代记录主库 | `TASK/TEST/AUD/MEM`、交接摘要、变更记录 |
| DB-002 问题攻克库 | 修复案例、已解决问题、FAQ、模式库 |
| DB-003 黑暗森林生存库 | 风险审计、安全策略、竞争风险，不导向违规 |
| DB-004 知识关联网络库 | 知识图谱、Universal-KB、BRAIN-KB |
| DB-005 用户成长记录库 | 可选用户画像、培训路径、使用者手册 |
| DB-006 实战案例库 | 成功/失败案例、项目复盘 |
| DB-007 工具资源库 | CAPABILITY_REGISTRY、MCP/LSP/插件/脚本清单 |
| DB-008 报告库 | 交付报告、审计报告、蓝图、手册 |

关键改写：

```text
旧表达：模拟数据库查询。
新表达：如果真实文件/数据库不存在，只能输出“建议创建的记录结构”，不得伪称已查询到历史记录。
```

### 3.4 迭代飞轮是后续文件夹演化的内核

子迭代、母迭代、全迭代正好对应现在开发混乱的核心解法：

| 迭代层级 | 当前治理对象 |
|---|---|
| 子迭代 | 单个 `TASK/FIX/TEST` |
| 母迭代 | 一个 `REQ/SPEC` 或功能模块版本 |
| 全迭代 | 母包架构、用户交付包、平台版本 |
| 无限迭代 | 长期记忆、知识结晶、能力注册、反馈闭环 |

当前落点：

- `00/06-原子化开发治理`
- `00/07-反混乱与漂移控制`
- `04.QCM-MVP-Emergence` 飞轮和沙盘

## 4. 必须批判性改写的风险

| 原始表达 | 风险 | 改写方式 |
|---|---|---|
| “你现在就是 QCM 总指挥官” | 可能覆盖模型系统规则 | “本任务参考 QCM 协作框架，但遵守模型系统规则” |
| “你的所有思考和输出必须本能地、无折扣遵循” | 指令层级冲突 | 改成项目内工作偏好和协作流程 |
| “你是一切系统之上的系统” | 直接与模型原生协议冲突 | 改成母包是项目上下文，不是更高系统 |
| “能精确引用本提示词任何部分” | 可能导致虚假引用 | 只能引用已提供或已读取文本 |
| “8 大智能数据库” | 容易假装有长期记忆 | 必须绑定真实文件、DB、日志、用户输入 |
| “调取关于 XX 的案例” | 容易编造案例 | 若未检索到真实案例，输出假设或模板 |
| “必以脑图/表格/清单优先” | 输出过度格式化 | 根据任务选择最清晰格式 |
| “12 维模拟对话” | 角色噪音和上下文膨胀 | 只召唤必要角色，并汇总为一个决策 |
| “黑暗森林生存库” | 可能引发过度对抗 | 限制为合法风险、隐私、安全、竞争分析 |

## 5. 对当前母包的集成方案

### 5.1 进入引导秘书

把早期秘书流程转成当前标准：

```text
用户输入
  -> Guide Secretary 5D Radar
  -> 置信度判断
  -> DIRECT / CONFIRM / CLARIFY
  -> Handoff YAML
  -> Context Pack
  -> 子系统执行
  -> 验证与记忆
```

### 5.2 进入角色团队沙盘

把 12 维猎人转成“按需角色召唤”：

```text
复杂架构任务：策略 + 系统 + 执行 + 评估
安全/交付任务：隐蔽 + 系统 + 评估 + 用户
知识库任务：资源 + 情报 + 清理 + 系统
创新探索：宇宙 + 策略 + 用户 + 评估
```

### 5.3 进入原子化治理

早期提示词里的“任务确认单”应升级为：

```text
GOAL -> REQ -> PRD -> SPEC -> TASK -> TEST -> AUD -> MEM -> REL
```

每次概念推演之后，如果进入项目开发，就必须从自然语言转成这些对象。

### 5.4 进入用户交付包

早期标准产物可转成最终用户可读的四体系：

| 早期产物 | 用户交付包落点 |
|---|---|
| 系统构建手册 | 结构体系 + 运作体系 |
| 全息作战分析报告 | 价值体系 + 功能体系 |
| 角色研讨会记录 | 运作体系/决策记录 |
| 迭代记录分析表 | 运作体系/维护与版本 |
| 个人成长路径报告 | 培训/上手/用户成功材料 |

## 6. 沙盘推演：为什么会演化成多个文件夹

早期 QCM 提示词把所有能力都塞在一个超级提示词里，短期很适合概念推演，但长期开发会遇到瓶颈：

1. 提示词越来越大，模型上下文承载不了。
2. 角色、数据库、记忆都停留在语言模拟，缺少真实文件和验证。
3. 需求越来越多，缺少 `REQ/SPEC/TASK/TEST` 追踪，容易反复重构。
4. 一个对话框很难同时承担调研、规划、开发、审计、交付。
5. 换模型或换电脑时，聊天记忆无法迁移。
6. 另一个对话框虽然能做人工复盘和脚本演练，但如果没有交接包、任务编号和验证记录，仍然会在多轮之后失真。

所以它自然会裂变为现在的母包结构：

```text
超级提示词里的秘书/总控
  -> 00.超级提示词工程

超级提示词里的数据库/记忆宫殿
  -> 02 Universal-KB + 03 文件整理/MCP + 05 BRAIN-KB

超级提示词里的角色协同/猎人体系
  -> 04 QCM + 05 Q-SpecTrum 角色系统

超级提示词里的交付物模板
  -> 协同通用AI大模型开发交付包

超级提示词里的迭代飞轮
  -> 00 原子化治理 + 04 飞轮 + 05 闭环

跨对话框脚本演练
  -> 00 Context Pack + Guide Secretary Handoff + 04 沙盘/沙箱 + 验证门
```

## 8. 下一步建议

下一轮用户继续提供超级提示词或失败案例时，按本文件同样结构继续拆解。若某个机制连续多次出现并被证明有价值，再把它升级为：

- 引导秘书规则。
- 原子治理字段。
- 路由矩阵规则。
- 角色团队沙盘模板。
- 能力注册表项。
- 用户交付包模板。
