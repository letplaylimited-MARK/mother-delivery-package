# Skill Configuration Expert v3 超级系统提示词解构

> 源材料：用户提供的“技能配置专家超级系统提示词工程 v3.0”。  
> 场景：用户在 AI 项目开发中发现，Agent 或角色再强，如果没有匹配到足够强、足够可调用、足够可验证的 Skill/MCP/LSP/插件/脚本/工作流，项目仍会停留在讨论、重构和反复修补。  
> 结论：此提示词应转译为母包的“技能配置阶段门”，并接入 `00/10 通用AI协作生态`，不能原样变成最高系统提示词。

## 1. 用户真实意图还原

用户不是只想“推荐几个开源库”。更深层目标是：

```text
自然语言项目需求
  -> 需求澄清
  -> 技能需求推导
  -> 开源/现有能力发现
  -> 评估与取舍
  -> 安装配置
  -> MCP/LSP/插件/脚本/工作流接入
  -> 集成测试
  -> 能力沉淀
  -> 用户交付包可复现
```

这解决的是母包目前最容易断裂的一层：能力层。

过去 QCM 偏“多角色协同思考”，SpecForge 偏“需求规格锻造”，而技能配置专家偏“能力如何落地”。三者应该串起来，而不是互相替代。

## 2. 与坊间提示词的差距判断

如果只看表层，这个提示词像常见的“帮我找工具/开源库/安装教程”的提示词；但它真正有价值的地方在于：

| 维度 | 常见提示词 | 本源提示词的价值 | 当前需要补强 |
|---|---|---|---|
| 需求理解 | 直接推荐工具 | 先提取项目、功能、技术栈、性能、约束 | 加入 PRD/SPEC 和任务编号 |
| 技能推导 | 关键词匹配 | 把需求转成技能需求清单 | 从关键词升级为产品/功能/工程/AI协作四层推导 |
| 开源寻找 | 凭印象列项目 | 要求许可证、活跃度、文档、社区 | 必须实时查询，禁止伪造 Star/日期/许可证 |
| 技能评估 | 主观推荐 | 七维度矩阵和权重 | 加入安全、许可证、AI可调用性、交付迁移 |
| 配置方案 | 给安装命令 | 安装、配置、集成、错误处理 | 加入能力卡、权限、验证、回滚、交付结论 |
| 工作流串联 | 较少处理 | 提到技能集成架构 | 明确 Skill <-> Workflow 双向转化 |
| 项目沉淀 | 停留在回答 | 输出完整文档 | 写入能力注册表、追踪矩阵、用户交付包 |

因此，它的价值不是“比坊间提示词更华丽”，而是更接近工程化能力治理。不过原提示词仍然需要补强证据、权限、验证、注册表和模型原生边界。

## 3. 原子机制拆解

| 原子机制 | 原提示词表达 | 可吸收程度 | 转译方式 |
|---|---|---|---|
| 角色身份 | 技能配置专家 | A | 保留为角色团队成员，不作为最高身份 |
| 四阶段流程 | 需求理解、技能寻找、技能评估、配置方案 | A | 转成 Skill Configuration Gate |
| 需求提取模板 | 项目概述、核心功能、技术栈、性能、约束 | A | 接入 SpecForge 与 Context Pack |
| 关键词推导 | 图像/NLP/数据/API/ML | B | 作为快速启发，不作为唯一判断 |
| 开源搜索策略 | 许可证、活跃度、文档、社区 | A | 加入实时证据要求 |
| 七维评估 | 功能、易用、性能、维护、社区、兼容、文档 | A | 扩展为十二维 |
| 配置方案 | 安装、配置、代码示例、注意事项 | A | 加入权限、失败处理、验证、交付迁移 |
| 集成架构 | 输入 -> 技能链 -> 输出 | A | 转为工作流编排和复合 Skill 沉淀 |
| 输出文档结构 | 技能配置方案文档 | A | 保留为阶段门输出物 |
| 质量控制 | 必需章节、备选、评估、可执行 | A | 加入反幻觉与证据审查 |

## 4. 关键概念重整

原提示词最大的问题不是流程，而是“技能”概念过宽。当前母包需要这样定义：

```text
Skill:
  可复用能力单元。
  可以是提示词、脚本、模板、工具调用、角色流程或混合方法。
  必须有触发条件、输入、输出、验证和失败处理。

Workflow:
  多个 Skill、工具、角色、阶段门按顺序和状态编排。
  稳定运行后可以沉淀成复合 Skill。

Agent:
  负责执行目标，可以调用 Skill/Workflow/MCP/LSP/Plugin。
  不等同于 Skill。

MCP/Plugin/LSP:
  是工具与事实通道。
  不是产品需求，也不是角色本身。

Capability:
  统一上位概念，所有可注册、可调用、可验证的能力都进入能力注册表。
```

这个边界非常重要。否则后续会出现：

- 以为“写了提示词”就等于有技能。
- 以为“装了插件”就等于形成工作流。
- 以为“Agent 能调用工具”就等于结果可验证。
- 以为“开源库可用”就等于可进入用户交付包。

## 5. 风险与冲突审查

| 风险 | 表现 | 处理 |
|---|---|---|
| 伪造开源指标 | 编造 Star、更新时间、许可证 | 必须实时搜索或标记未验证 |
| 关键词误配 | 看到“图像”就推荐图像库，但需求可能只是 UI 图片 | 先经 SpecForge/Guide Secretary 澄清 |
| 只选库不集成 | 推荐项目后没有配置、接口、测试 | 必须产出能力卡和集成测试 |
| 许可证风险 | 商业交付时使用不合规依赖 | 加入许可证与交付审查 |
| 安全风险 | 插件/MCP 需要密钥、网络、账号 | 纳入权限等级和密钥管理 |
| 迁移失败 | 只在当前电脑能跑 | 路径、依赖、环境变量、容器化检查 |
| 技能污染 | 把临时提示词当正式能力 | 先标记 experimental，试跑后升级 |
| 工作流僵化 | 固定流程压过真实需求 | 由引导秘书按意图选择最小阶段门 |

## 6. 与 QCM、SpecForge 的串联

```text
QCM:
  用户想法还不清楚时，用秘书、角色团队、沙盘、第一性原理推演方向。

SpecForge:
  方向变成项目需求后，把 PRD/SPEC/验收标准锻造成可测试对象。

Skill Configuration Expert:
  根据 PRD/SPEC 推导需要哪些 Skill/MCP/LSP/插件/脚本/工作流，并完成选型、配置、集成。

Atomic Governance:
  把能力配置结果绑定 TASK/TEST/AUD/MEM，防止后续漂移。

用户交付包:
  只保留具体项目需要的能力、配置、验证和运作说明。
```

三者的分工可以简化成：

```text
QCM 让问题被想清楚。
SpecForge 让需求被写清楚。
Skill Configuration 让能力被配清楚。
```

## 8. 沙盘推演

### 场景 A：用户说“我要做一个 AI 文件整理工具”

```text
Guide Secretary:
  识别为 PROJECT_INITIATION + SKILL_CONFIGURATION。

SpecForge:
  澄清目标用户、核心痛点、范围、不做什么、验收标准。

Skill Configuration:
  推导能力：
    - 文件扫描 Skill
    - 文档解析 Skill
    - 向量检索 Skill
    - 分类规则 Skill
    - MCP 工具调用
    - 配置管理
    - 集成测试

能力匹配:
  先查 03 是否已有搜索、整理、MemoryOS、MCP 工具。
  若已有，不重复引入新库。

交付:
  用户交付包只写项目需要的运行命令、配置模板、验证方式。
```

### 场景 B：用户说“Agent 为什么很强但项目还是卡住”

```text
诊断:
  Agent 是执行者，不是能力库本身。
  卡住原因可能是 Skill 缺失、工具不可调用、LSP/MCP 未接入、验证缺失、工作流没有状态。

处理:
  进入 CAPABILITY_GAP_REVIEW。
  列出现有能力、缺失能力、重复能力、不可验证能力。
  重新注册能力卡，补验证，拆工作流。
```

## 11. 最终判断

这个源提示词的核心价值很高。它补的是母包从“会思考、会写规格”到“会选择和配置真实能力”的关键层。

但它不能停留在“技能推荐文档”。真正进入母包后，必须成为：

```text
需求 -> 技能需求 -> 候选能力 -> 评估矩阵 -> 能力卡 -> 配置方案 -> 集成工作流 -> 验证证据 -> 交付沉淀
```

这样，通用 AI 大模型不会被取代，反而会因为有清晰的能力地图、调用边界和验证证据而变得更强。
