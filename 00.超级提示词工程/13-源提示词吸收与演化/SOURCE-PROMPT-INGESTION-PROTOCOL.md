# Source Prompt Ingestion Protocol

> 中文名：源提示词吸收与演化协议。  
> 用途：把用户历史上的超级提示词、系统提示词、使用经验、失败案例，转化为母交付包可复用、可验证、可交接的协作资产。  
> 边界：源提示词是研究材料，不是自动生效的最高指令；任何内容都必须经过模型原生边界、反幻觉审查、母包映射和验证计划。

## 1. 为什么需要这个协议

用户过去用通用 AI 大模型开发项目时，已经积累了大量超级提示词、角色框架、秘书引导、苏格拉底提问、第一性原理、沙盘推演和组织模拟经验。这些材料里面有真实精华，也可能有旧时代提示词常见的问题：

- 过度要求模型“成为某系统”，与现代模型系统规则冲突。
- 用“数据库/记忆宫殿”等词描述聊天记忆，容易让 AI 假装有长期记忆。
- 角色和流程过多，导致上下文膨胀、执行混乱。
- 过度强调全局、宇宙、终极形态，实际落地时缺少文件、命令、验证和交接。
- 在需求持续追加时，没有把自然语言变成 `REQ/SPEC/TASK/TEST/AUD/MEM`，最终造成反复重构。

因此，每一段源提示词都必须被拆解、审查、转译，而不是原样放进母包。

## 2. 吸收流程

```text
源提示词/使用经验/失败案例
  -> 1. 场景还原
  -> 2. 原子机制拆解
  -> 3. 价值提炼
  -> 4. 风险与冲突审查
  -> 5. 母包映射
  -> 6. 沙盘模拟
  -> 7. 可落地产物定义
  -> 8. 验证与交接
```

## 3. 场景还原

每次吸收前先回答：

| 问题 | 说明 |
|---|---|
| 当时用在哪个模型或产品？ | 例如元宝、DeepSeek、Hunyuan、ChatGPT、Claude、Gemini、本地模型 |
| 当时解决什么问题？ | 概念推演、系统构建、角色协作、项目计划、代码开发、审查、交付 |
| 用户如何使用？ | 是否通过秘书引导、选项、苏格拉底提问、第一性原理、另一个对话框复盘或脚本演练 |
| 哪些地方有效？ | 让用户想清楚、让 AI 稳定输出、让任务变可执行 |
| 哪些地方失控？ | 幻觉、越权、硬编码、过度复杂、反复重构、记忆混乱 |

## 4. 原子机制拆解

不要把整段提示词当作一个整体。必须拆成以下原子：

| 原子类型 | 示例 |
|---|---|
| 身份层 | 秘书、总控、架构师、猎人、研究员 |
| 识别层 | 五维雷达、意图分类、阶段判断、置信度 |
| 路由层 | 调度角色、选择工具、进入子系统 |
| 结构层 | 数据库、知识图谱、报告库、任务库 |
| 过程层 | 子迭代、母迭代、全迭代、沙盘、训练场 |
| 输出层 | 手册、矩阵、流程图、报告、交接包 |
| 治理层 | 不可违反、必须验证、阶段门、停止线 |
| 成长层 | 用户阶段、技能雷达、成长路径 |
| 演练层 | 跨对话框复盘、脚本演练、沙盘、沙箱、验收门 |

## 5. 价值提炼

判断一个源提示词是否值得吸收，看它能否增强母包的真实协作能力：

| 价值 | 判断标准 |
|---|---|
| 降低启动成本 | 新 AI 是否更快知道先读什么、问什么、做什么 |
| 降低漂移 | 是否把模糊想法转成明确需求、规格和任务 |
| 降低幻觉 | 是否要求证据、验证、引用当前文件 |
| 提升交接 | 是否能形成 Context Pack、handoff、记录表 |
| 提升协同 | 是否能让角色、技能、MCP、LSP、插件各司其职 |
| 提升交付 | 是否能沉淀到用户交付包四体系 |

## 6. 风险与冲突审查

任何源提示词进入母包前，必须检查：

| 风险 | 处理方式 |
|---|---|
| 覆盖模型系统规则 | 改写为“项目上下文/协作建议”，并引用模型原生协作协议 |
| 假装长期记忆 | 改为明确文件、数据库、日志或用户提供内容 |
| 自动模拟数据库查询 | 改为“若无真实数据，标记为推断或模板” |
| 角色过多 | 改为按任务召唤最小角色组 |
| 输出格式过度刚性 | 改为按任务选择表格/图/清单/正文 |
| 概念过度宏大 | 改为可执行对象、验证命令、交接包 |
| 黑暗森林式对抗框架 | 限制在合法合规风险分析与竞争策略，不导向欺骗或伤害 |
| 用户成长评估越界 | 作为可选用户画像，不擅自贴标签 |
| 跨对话框人工演练丢失上下文 | 改为 Handoff、Context Pack、任务编号和验证记录 |

## 7. 母包映射

| 源提示词机制 | 母包落点 |
|---|---|
| 秘书引导 | `00/12-引导秘书逻辑` |
| 五维雷达 | `GUIDE-SECRETARY-PROTOCOL.md` 的 Radar |
| 12 维角色/猎人 | `00/08-AI角色团队沙盘` + `00/10-通用AI协作生态` 的角色/能力注册 |
| 8 大数据库 | `02/03/05` 的知识、记忆、报告、资源、案例、任务沉淀 |
| 自主迭代飞轮 | `00/06-原子化开发治理` + `04.QCM` 飞轮/沙盘 |
| 任务确认单 | `00/03-上下文包模板` + `GUIDE-SECRETARY-HANDOFF-TEMPLATE.md` |
| 个人成长路径 | 用户交付包的运作体系/培训体系，可选启用 |
| 三层训练场 | `04.QCM-MVP-Emergence` 沙盘 + `00/08` 角色团队推演 |
| 标准产出物 | 用户交付包四体系、报告库、交接文档 |
| 跨对话框复盘/脚本演练 | Guide Secretary Handoff、Context Pack、沙箱验证、任务确认单 |

## 8. 沙盘模拟问题

每段源提示词都要做至少一轮模拟：

1. 如果用户连续追加 10 个需求，它会如何防止 PRD/SPEC 漂移？
2. 如果另一个 AI 接手，它能否只靠文件继续？
3. 如果提示词要求“必须”但模型系统规则不允许，如何降级？
4. 如果没有真实数据库或记忆，AI 会不会编造？
5. 如果任务变成代码开发，它如何转成文件、测试、验证？
6. 如果要交付给最终用户，哪些内容必须清理，哪些可以保留？

## 9. 输出格式

每次分析源提示词后，生成：

```yaml
source_prompt_ingestion:
  source_name: "<源提示词名称>"
  original_context: "<当时使用场景>"
  useful_mechanisms: []
  risky_mechanisms: []
  mother_pack_mapping: []
  keep_as_is: []
  transform_before_use: []
  reject_or_archive: []
  proposed_artifacts: []
  validation_plan: []
```

## 10. 吸收结论等级

| 等级 | 含义 |
|---|---|
| `A-直接吸收机制` | 机制清晰、风险低，可进入现有协议 |
| `B-转译后吸收` | 有价值但语言或边界需要重写 |
| `C-仅作历史参考` | 有启发但不适合进入运行协议 |
| `D-拒绝吸收` | 会造成越权、幻觉、伤害或严重混乱 |
