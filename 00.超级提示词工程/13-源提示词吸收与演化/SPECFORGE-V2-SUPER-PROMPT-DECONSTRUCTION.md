# SpecForge v2 Super Prompt Deconstruction

> 来源：用户提供的 `SpecForge - 终极Spec锻造系统`。  
> 场景：用户曾用此类超级系统提示词，把模糊产品想法通过结构化追问转成可交付开发与测试的 PRD/SPEC 文档。  
> 结论：SpecForge 是母交付包中“规格锻造、验收标准、变更控制、交付质量”的关键源提示词，应从历史提示词转译为 `00/06 原子化开发治理` 的 PRD/SPEC 阶段门，而不是原样作为更高系统提示词。

## 1. 场景还原

SpecForge 的真实用途，是在用户已有产品想法但尚未形成开发契约时，强制把自然语言变成可开发、可测试、可评审的规格文档。

```text
模糊想法 / 产品概念
  -> 蓝图锚定：问题、用户、指标、边界
  -> 功能锻造：用户故事、流程、异常、验收标准、业务规则
  -> 质量熔炼：性能、安全、兼容性、UX、数据、接口
  -> 淬火交付：完整性扫描、一致性审查、风险标注、Markdown 导出
```

它和 QCM 的关系：

| 体系 | 核心作用 | 母包角色 |
|---|---|---|
| QCM | 概念推演、角色沙盘、协同评审、涌现判断 | 让想法变清楚 |
| SpecForge | 追问细节、冻结边界、生成 PRD/SPEC、绑定验收 | 让想法变可交付 |
| Atomic Governance | 编号、追踪、验证、审计、记忆 | 让交付可持续 |

## 2. 原子机制拆解

| 原提示词模块 | 原子机制 | 当前判断 |
|---|---|---|
| 核心宪章：交付至上 | 每轮必须推进 Spec 内容 | 可吸收，但不能强制每次对话都改文档 |
| 细节追问 | 将“好用/快速/安全”转成可测标准 | 直接吸收为 SPEC 澄清门 |
| 实时建档 | 确认内容立即落入章节 | 转译为 PRD/SPEC 工件更新 |
| Spec 主框架 | 标准 PRD/SPEC 章节模板 | 可变成模板，但需支持不同项目裁剪 |
| 四步交付法 | 蓝图、功能、质量、淬火 | 直接映射到 `CLARIFIED -> PRD_READY -> SPEC_READY -> VERIFIED` |
| 模式识别加速 | 识别常见系统类型并预加载模块 | 可作为能力，但必须标记为建议模板 |
| 冲突实时预警 | 功能、性能、约束冲突检测 | 直接吸收为审计规则 |
| 决策追踪 | 记录关键决策和理由 | 映射到 ADR/决策日志 |
| 版本快照 | 节点快照可回溯 | 映射到 HANDOFF、Snapshot、版本记录 |
| 质量清单 | 功能优先级、验收标准、性能指标等 | 直接吸收为 SPEC_READY Gate |

## 3. 真正值得保留的精华

### 3.1 交付至上，但要受阶段门约束

SpecForge 的“交付至上”很有价值，因为它防止 AI 长期停留在概念讨论。但原始写法“每次对话必须推进 Spec 文档”过于刚性。母包中应改为：

```text
当任务处于 PRD/SPEC 锻造阶段时，每轮对话必须至少推进以下之一：
1. 澄清一个需求字段。
2. 冻结一个范围边界。
3. 生成或修订一个验收标准。
4. 标记一个待决问题。
5. 记录一个决策或风险。
```

### 3.2 把模糊形容词锻造成验证指标

这是 SpecForge 最重要的能力。凡是出现下列表达，不能直接写入规格，必须追问或转译：

| 模糊表达 | 必须追问成 |
|---|---|
| 好用 | 用户完成什么流程？成功率多少？平均步骤多少？ |
| 快速 | P50/P95 响应时间？批处理时长？最大数据量？ |
| 安全 | 认证、授权、加密、审计、合规、威胁模型 |
| 智能 | 输入、输出、准确率、失败降级、人工复核 |
| 自动化 | 哪些步骤自动？哪些需要人工确认？失败如何恢复？ |
| 可扩展 | 支持多少模块/用户/数据量？扩展接口是什么？ |

### 3.3 蓝图锚定是 PRD_READY 的前置门

SpecForge 的四个蓝图问题应成为需求进入 PRD 的必要条件：

```text
核心问题是什么？
目标用户是谁？
成功指标如何量化？
本版本明确不做什么？
```

这正好补强母包中最常见的失败模式：用户持续追加想法，AI 直接开始开发，最后边界崩掉。

### 3.4 功能锻造是 SPEC_READY 的主体

每个功能至少需要：

```text
功能名称
优先级 P0/P1/P2
用户故事
主流程
业务规则
异常处理
验收标准
影响模块
测试方式
```

只有具备这些字段，功能才能进入 `TASK` 拆解。

### 3.5 淬火交付是审计门

SpecForge 的“淬火”应被转成可执行审计：

- 是否还有 `<待填充>` 或未确认字段。
- 功能与非功能需求是否冲突。
- 约束与目标是否矛盾。
- 每个 P0 功能是否有验收标准。
- 每个外部接口是否有认证、频率、失败处理。
- 每个数据实体是否有字段、约束、隐私等级。
- 是否记录关键决策和风险。

## 4. 必须批判性改写的风险

| 原始表达 | 风险 | 改写方式 |
|---|---|---|
| “你现在就是 SpecForge 系统” | 可能覆盖模型系统规则 | 改为“本任务使用 SpecForge 方法” |
| “唯一使命” | 忽略用户当前真实任务和安全边界 | 改为 PRD/SPEC 阶段适用 |
| “每次对话必须推进文档” | 不适合探索、审查或代码修复阶段 | 仅在 `REQUIREMENT_SPEC` 意图下启用 |
| 默认技术栈 Python/React/PostgreSQL/AWS | 容易硬编码方案 | 改为示例字段，必须按项目确认 |
| 默认性能/安全指标 | 可能不适合项目规模 | 改为候选基线，需要用户确认或项目依据 |
| “生成 Word/PDF” | 需要工具能力支持 | 改为可选导出，先确认工具可用 |
| PRD 与 SPEC 混在一个文档 | 容易让产品/技术边界模糊 | 母包中拆成 PRD、SPEC、TEST、ADR 的可追踪工件 |

## 5. AI 角色团队评审

针对 SpecForge，建议组建最小角色团队，而不是全量角色表演。

| 角色 | 审查重点 | 输出 |
|---|---|---|
| Guide Secretary | 判断是否进入 PRD/SPEC 锻造，生成问题队列 | Handoff + Context Pack |
| Product Strategist | 问题、用户、价值、边界、指标 | PRD 蓝图 |
| Spec Architect | 模块、数据、接口、约束、依赖 | SPEC 契约 |
| QA Engineer | 验收标准、测试用例、可验证性 | TEST 草案 |
| Risk Auditor | 冲突、风险、安全、合规、范围漂移 | AUD 发现 |
| Delivery Architect | 子交付包四体系映射 | 交付结构 |

### 5.1 沙盘评审问题

```text
Product Strategist:
  这个需求解决的真实痛点是否清楚？
  成功指标是否可衡量？

Spec Architect:
  当前功能描述能否拆成模块、接口、数据和配置？
  有哪些技术约束是假设而不是事实？

QA Engineer:
  每个 P0 功能是否有可执行验收标准？
  是否存在无法测试的描述？

Risk Auditor:
  哪些功能与性能、安全、时间、预算冲突？
  哪些范围外内容最容易被后续追加？

Delivery Architect:
  哪些内容进入用户交付包的价值/功能/结构/运作体系？
  哪些母包资料不应该交给最终用户？
```

## 6. 与当前母包的集成方案

### 6.1 进入引导秘书

SpecForge 不是默认每次启动。只有当引导秘书识别到以下意图时启用：

```text
REQUIREMENT_SPEC
PROJECT_INITIATION
USER_DELIVERY
复杂功能新增
需求变更影响分析
验收标准缺失
PRD/SPEC 漂移
```

### 6.2 进入原子化治理

SpecForge 输出必须拆成原子对象：

```text
GOAL  -> 产品目标
USER  -> 用户画像
SCN   -> 使用场景
REQ   -> 原子需求
PRD   -> 产品条目
SPEC  -> 技术规格
TEST  -> 验收标准/测试用例
ADR   -> 关键决策
AUD   -> 风险与冲突
TASK  -> 实施任务
MEM   -> 经验沉淀
REL   -> 交付版本
```

### 6.3 进入用户交付包四体系

| SpecForge 章节 | 子交付包落点 |
|---|---|
| 文档概述、修订历史、术语 | `04-运作体系` / `docs/` |
| 产品背景、目标、指标、用户画像 | `01-价值体系` |
| 功能需求、用户故事、流程、业务规则 | `02-功能体系` |
| 非功能需求、数据、接口、约束 | `03-结构体系` + `04-运作体系` |
| 风险与应对、决策日志、验收清单 | `04-运作体系` / `HANDOFF.md` |
| 竞品分析、用户调研 | `01-价值体系` / `docs/` |

### 6.4 进入 Q-SpecTrum

在 `05` 中，SpecForge 对应以下角色和能力：

```text
Secretary      -> 判断是否进入 SpecForge
SPEC family    -> 架构/标准/合规/桥接
QCM Q01/Q03    -> 产品结构与文档生成
QCM Q06        -> 风险与验收审计
BRAIN-KB       -> 保存决策、模式、限制
```

### 6.5 进入 QCM

在 `04` 中，SpecForge 可作为沙盘输出的“淬火门”：

```text
角色沙盘提出方案
  -> SpecForge 蓝图锚定
  -> 功能锻造
  -> 质量熔炼
  -> 淬火审计
  -> 才允许进入开发任务
```

## 7. 与 QCM 源提示词的组合方式

```text
QCM: 让用户想清楚
  -> 秘书引导、苏格拉底提问、第一性原理、多角色沙盘

SpecForge: 让需求写清楚
  -> PRD/SPEC 模板、可测验收、数据接口、风险与约束

Atomic Governance: 让开发做清楚
  -> ID、追踪矩阵、任务图、测试、审计、记忆

User Delivery Pack: 让成果交清楚
  -> 价值体系、功能体系、结构体系、运作体系
```

这四者的融合，是母包从“对话推演”走向“工程交付”的关键。

## 9. 下一步

SpecForge 应升级为母包中的正式 PRD/SPEC Gate。下一步不是继续扩写提示词，而是建立：

- `SPECFORGE-PRD-SPEC-GATE.md`
- `PRD.md` 模板
- `SPEC.md` 模板
- `ACCEPTANCE-TESTS.md` 模板
- `DECISION-LOG.md` 模板
- 追踪矩阵字段：`REQ -> PRD -> SPEC -> TEST -> TASK -> AUD`
