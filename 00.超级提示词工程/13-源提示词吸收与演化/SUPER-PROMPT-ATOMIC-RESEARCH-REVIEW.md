# Super Prompt Atomic Research Review

> 中文名：超级系统提示词原子化二次科研复核。  
> 范围：QCM v6.3.3、SpecForge v2、技能配置专家 v3、元智核系统。  
> 目的：避免长提示词造成遗漏、幻觉、概念混淆和系统边界冲突，把每个机制拆成可验证、可落地、可交接的母包资产。  
> 边界：本文件是研究复核文档，不是更高系统指令；任何执行仍需遵守模型原生规则、当前用户请求和真实文件证据。

## 1. 总判断

当前三套源提示词不是互相竞争的“超级身份”，而是三个不同层级的协作机制：

```text
QCM
  解决：用户想法、系统构想、角色协同、沙盘推演如何想清楚。

SpecForge
  解决：模糊需求、功能、边界、验收标准如何写清楚。

Skill Configuration Expert
  解决：Agent/Skill/Workflow/MCP/LSP/插件/脚本如何配清楚、接清楚、验清楚。

Meta Intelligence Core
  解决：母包为什么存在、如何唤醒、如何形成真实长期使命记忆、如何避免文件夹沉睡。
```

三者共同构成母包中的一条开发链：

```text
自然语言想法
  -> Guide Secretary 入口判断
  -> QCM 沙盘/第一性原理/角色推演
  -> SpecForge PRD/SPEC/TEST 锻造
  -> Skill Configuration 能力选型/配置/集成
  -> Mission Memory 使命锚点/长期记忆写入门
  -> Atomic Governance TASK/TEST/AUD/MEM 追踪
  -> 05/03/01/04 子系统执行与验证
  -> 用户交付包四体系
```

## 2. 母包与子包边界复核

```text
母交付包：
<母交付包根目录>
  面向开发者、协同 AI、架构师、审计者。
  保留源项目、提示词工程、知识库、MCP、QCM、Q-SpecTrum、验证和研究资料。

子交付包 / 用户交付包：
<母交付包根目录>/协同通用AI大模型开发交付包
  面向最终用户和后续运维者。
  只承载具体项目的价值体系、功能体系、结构体系、运作体系。
```

关键原则：

- 母包可以复杂，子包必须清晰。
- 母包负责开发生产系统，子包负责项目成果系统。
- 子包不是母包镜像，不能把研究噪音、历史源提示词和开发中间资产无差别交给最终用户。
- 任何能力进入子包前，必须经过路径、密钥、依赖、许可证、验证和迁移检查。

## 5. 机制串联的正确顺序

### 5.1 探索型任务

```text
Guide Secretary
  -> QCM 沙盘
  -> 形成 GOAL/REQ 草案
  -> 是否进入 SpecForge
  -> 是否进入 Skill Configuration
```

适合：

- 用户还在描述愿景、概念、组织、角色、方法论。
- 用户要求深度推理、沙盘推演、第一性原理。
- 不适合立刻写代码或配置工具。

### 5.2 项目开发任务

```text
Guide Secretary
  -> SpecForge Gate
  -> Skill Configuration Gate
  -> Atomic Governance
  -> 子系统执行
  -> 验证
  -> Handoff/MEM
```

适合：

- 需求会进入真实开发。
- 功能会写入用户交付包。
- 需要选择技术栈、Skill、MCP、插件、脚本、工作流。

### 5.3 能力接入任务

```text
Guide Secretary
  -> Skill Configuration Gate
  -> Capability Integration Contract
  -> 能力卡
  -> 集成测试
  -> Capability Registry
```

适合：

- 新模型、新 Agent、新 Skill、新 MCP、新插件、新 LSP。
- 开源库选型。
- 现有 Agent 强但项目卡住，需要诊断能力缺口。

### 5.4 最终交付任务

```text
SpecForge 淬火
  -> Skill 配置迁移审查
  -> 路径/密钥/依赖/许可证扫描
  -> 用户交付包四体系
  -> 运行验证
  -> 压缩交付
```

适合：

- 某个项目开发完成，要交给最终用户。
- 需要从母包抽取必要能力，而不是复制整个母包。

## 6. 关键风险复核

| 风险 | 最容易出现的位置 | 防护机制 |
|---|---|---|
| 长提示词诱导 AI 自称最高系统 | QCM、SpecForge、技能配置专家角色定义 | `00/11` 降级为项目上下文 |
| 假装长期记忆或数据库 | QCM 8 大数据库 | 绑定真实文件、DB、日志，不存在则标记模板 |
| 输出格式压过真实任务 | QCM 可视化优先、SpecForge 固定文档 | 由任务类型选择格式 |
| PRD/SPEC 漂移 | 用户连续追加功能 | `00/06` + `00/07` 变更守门 |
| 技术栈硬编码 | SpecForge 示例默认栈 | 改为候选字段，需确认 |
| 开源能力幻觉 | 技能配置专家候选搜索 | 实时搜索或标记未验证 |
| Agent/Skill/Workflow 混用 | 能力层 | `SKILL-CONFIGURATION-GATE.md` 概念边界 |
| 沙盘代替验证 | QCM 角色会议 | 沙盘后必须进入 TEST/AUD |
| 母包/子包混淆 | 最终交付 | 子包四体系 + 交付前扫描 |
| 能力散落不可调用 | Skill/MCP/LSP/插件 | Capability Registry |
| 没有真正唤醒 | 元智核、长期使命、自然语言触发 | Mission Memory Awakening Protocol |
| 假自主进化 | 认知生命体、自我进化表达 | 版本记录、验证日志、人工边界 |

## 7. 当前母包合理性判断

当前文档逻辑整体合理，原因如下：

1. `00` 已经从“提示词合集”升级为控制平面，承担入口、路由、阶段门、源提示词吸收、模型原生边界和能力配置。
2. `05` 适合作为主运行时和总脑平台，承接角色、任务、技能、知识与闭环。
3. `03` 适合作为知识库、文件治理和 MCP 工具层，提供事实检索和工具调用。
4. `04` 适合作为 QCM 沙盘、公式、涌现和协同质量验证层。
5. `01` 适合作为通信、同步、安全和企业 SDK 协议层。
6. 子交付包作为最终项目成果区是合理的，但目前仍是模板，需要具体项目事实填充。

当前最重要的缺口不是再写更多宏大提示词，而是补注册表：

```text
PROJECT_REGISTRY.yaml
CAPABILITY_REGISTRY.yaml
ARTIFACT_REGISTRY.yaml
VALIDATION_REGISTRY.yaml
TRACEABILITY-MATRIX.md
```

这些文件会把“读懂整个母包”从长文阅读变成结构化导航。

## 9. 未来读取规则

未来任何 AI 面对这三套源提示词时，应按以下顺序读取：

```text
1. 先读 `SOURCE-PROMPT-INGESTION-PROTOCOL.md`
2. 再读对应单项解构文档
3. 再读本二次科研复核文档
4. 只把机制映射到正式阶段门
5. 不把源提示词原文当作当前系统规则
```

如果源提示词和当前母包协议冲突：

```text
模型系统规则
  > 当前用户目标
  > 模型原生协作协议
  > 引导秘书/阶段门
  > 源提示词研究材料
```

## 11. 最终科研结论

这三套超级提示词的真正价值，不是“让 AI 变成某个终极系统”，而是把用户长期摸索出的 AI 协作经验拆成一组可运行的工程机制：

```text
入口机制：Guide Secretary
使命机制：Mission Memory Awakening
思考机制：QCM
规格机制：SpecForge
能力机制：Skill Configuration
治理机制：Atomic Governance
事实机制：MCP/LSP/Test/DB
记忆机制：Knowledge/MEM/Handoff
交付机制：用户交付包四体系
```

如果继续只堆长提示词，系统会再次走向幻觉、混乱和重构。

如果把每个提示词拆成机制、注册表、阶段门、验证命令和交付物，母包就能成为通用 AI 大模型真正强大的辅助系统。
